# The L2 regression chain — checks that need a real cluster, and cannot run in PR CI.
#
# Companion to L0-CHAIN.txt. Split because the two have genuinely different triggers, not because
# L2 matters less: the load-bearing security negatives (egress actually denied, admission actually
# rejecting, isolation actually isolating) all live here. L0 proves a manifest is well-formed; L2 is
# the only thing that proves it is enforced. That distinction is LSN-006, and it is why a lesson may
# legitimately be closed by a script in this file even though no pull request runs it.
#
# Each line takes a --context argument. Every one of these is a DESTRUCTIVE test target: they apply
# deliberately-bad RBAC, delete pods, and exercise denial paths. The guard in each script is an
# anchored `case` on gke-scratch-* and invariants-gate.py asserts it stays anchored — a substring
# match is LSN-005, and the live GKE cluster is one `*` away. That the accepted set is now a single
# anchor and not two is a STRENGTHENING: the guards accept strictly fewer contexts than they did.
#
# Every line CARRIES its own context, still, even though every line now carries the SAME one.
#
# The single target is the end of a two-step consolidation. There used to be two clusters, because
# precondition P4 meant neither could serve the whole file: one hosted the operator on a dataplane
# that accepted NetworkPolicy and enforced none of it, the other enforced but hosted no operator.
# They differed in two create-time knobs, dataplane and node count, which are orthogonal — so up.sh
# built their union and there was one. On 2026-07-26 that union moved off the laptop to a remote GKE
# cluster (dev/cluster/up.sh — Dataplane V2, 2 nodes, Workload Identity), which changes where it runs
# and not what it is. Running several control planes on one laptop VM is also what LSN-026 cost us:
# three FALSE security failures from memory pressure alone, on a substrate no longer in the loop.
#
# The per-line context is NOT collapsed back into the run loop now that the values agree. It was a
# run-loop default once. That was a single-definition-site violation dressed as a convenience: the
# paragraph here explained that the targets differ and then handed the reader one loop that gave
# every line the same one. Followed literally on 2026-07-25 it sent `closed-allowlist-l2.sh` and
# `multi-agent-namespace-l2.sh` at the operator-less cluster, where both correctly returned
# P1-UNVERIFIABLE (rc 3) — two of six lines silently not run, and only visibly so because P1 refuses
# to guess. A default target is a guess about which cluster a check needs; the check knows, so the
# line says. That the guess would currently be RIGHT is exactly why re-introducing it would be hard
# to notice, and the next time the targets diverge is the run nobody would check.
#
# Run:  while read -r c; do case "$c" in ''|\#*) continue ;; esac; eval "$c"; done < dev/L2-CHAIN.txt
#
# Precondition P1 applies to every line that tests a DEPLOYED image, which is every line above the
# Phase 9 heading: `bash dev/cluster/reload-images.sh <what> <ctx>` builds, pushes, and deploys BY
# DIGEST, then P1 asserts the running imageID digest equals the build under test. A green here
# against a stale image is LSN-001, and no line of this file can detect that on its own — deploying
# by digest is what makes that trap unrepresentable rather than merely detected.
#
# The qualifier is new and it is a narrowing of scope, not of rigour. A CLIENT-SIDE probe — one that
# compiles the working tree and connects to the cluster as a client, rather than asserting against
# something running in a pod — has the working tree as its build under test by construction, which
# is the property P1 exists to establish. Demanding P1 there would mean deploying an image the check
# never looks at, and a precondition satisfied by an irrelevant act is worse than no precondition:
# it reads as coverage. Each such line says so in its own header and says what replaces P1. When the
# component a client-side probe stands in for becomes reachable in a pod, its successor check needs
# P1 in full, and the header names that successor.

# --- the standing regression suite ----------------------------------------------------------
# The standing line is the LAST CLOSED PHASE'S GATE, and nothing else. Phase 8 closed on 2026-07-27
# and this line still said verify-phase7.sh until 2026-07-30, which cost two things that are worth
# naming because neither is visible from the chain file.
#
# The first is coverage: verify-phase7.sh reaches phases 2-6, so for three phases the standing
# regression did not include the six Phase-8 suites at all. They were still run — they are listed
# individually below — but they were run as Phase 8's own evidence rather than as the floor every
# later phase has to clear, which is a different claim about the same commands.
#
# The second is subtler and is the reason this comment is this long. invariants-gate.py derives the
# set of scripts it lints for declared preconditions from the TRANSITIVE CLOSURE OF THIS FILE
# (_l2_scripts_in_scope). A phase gate that is in no chain line and that nothing else calls is
# therefore outside that closure: verify-phase8.sh, the single script that renders Phase 8's verdict,
# was never once asked which artifact it was judging. The lint was not broken and the script happens
# to declare its preconditions properly; the point is that nothing checked, for three phases, and the
# only way to find that out was to ask why the standing line was a phase behind.
#
# So: verify-phase8.sh is the whole prior build in one command. It runs verify-phase7.sh (=> phases
# 2-6, chaos C1-C4, 03 §11 negative attenuation, the goldens and `go test ./...`) and all six Phase-8
# suites. It is listed FIRST because a phase's new L2 evidence is worth nothing if it was gathered on
# a cluster where the previous phases had already broken.
bash dev/verify/verify-phase8.sh gke-scratch-kube-agents-dev

# verify-phase7.sh stays a line of its own even though the line above reaches it, and the reason is
# not sentiment. invariants-gate.py's check_closed_lessons_are_executable resolves chain lines
# LITERALLY — it does not follow delegation, unlike _l2_scripts_in_scope four hundred lines away in
# the same file — and dropping this line turned LSN-013 and LSN-028 red within one run, both of them
# closed years of build-time ago against verify-phase7.sh as their mechanizing artifact.
#
# The first instinct was that the check is coarse and should follow delegation. It should not, and
# the argument is the same one written under the Phase 8 heading below: verify-phase8.sh runs
# verify-phase7.sh only when P1 resolves, so a delegated call is a CONDITIONAL one. "Named by a chain
# line" means "runs every time the chain runs", and that is a stronger and more useful property than
# "is reachable". A lesson mechanized by an artifact that runs only when a precondition happens to
# hold is a lesson that can silently stop being mechanized on a cluster with a stale image.
bash dev/verify/verify-phase7.sh gke-scratch-kube-agents-dev

# --- Phase 9 L2 checks --------------------------------------------------------------------------
# V-GAT-022: classification reads live state, not the payload. A CLIENT-SIDE probe (see the P1 note
# above): it drives classify.ClientLiveState — the production LiveState — against this cluster from
# the working tree, because the broker's pipeline is still UnavailablePipeline{} until P9-T7c-3d and
# no deployed surface reaches the classifier yet. What makes it L2 rather than L1 is what only a
# real cluster has: GKE's full discovery surface for the blast-radius denominator, real RBAC for the
# skip-don't-refuse path, and real admission deciding a namespace's final label set. Its successor
# is the end-to-end form in broker-execute-l2.sh (P9-T9), which WILL need P1.
bash dev/verify/classify-live-state-l2.sh gke-scratch-kube-agents-dev

# V-REV-010: the recreate downgrade follows the LIVE owner graph. Another CLIENT-SIDE probe with the
# same P1 waiver and the same named successor. Three things make it L2 and not a bigger envtest:
# GKE's real discovery surface, against which the index's "any kind I cannot list fails the whole
# scan" clause has a cost worth measuring; real RBAC, so the Forbidden branch is reachable by
# something other than a stub; and a real garbage collector, which is the only way to DEMONSTRATE
# the harm — delete an owner, watch the dependent be destroyed, recreate the owner and watch it stay
# destroyed. That is the state a `recreate` plan would have reported as a completed undo.
bash dev/verify/reference-index-l2.sh gke-scratch-kube-agents-dev

# V-PRO-027: verification evidence is READ FROM THE CLUSTER. The third client-side probe, same P1
# waiver, same named successor. Its L1 half runs under `make test` and is a real result — it proves
# the prober reads the right fields. It cannot prove anything ever writes them, because envtest runs
# an API server and no controllers, so every status the L1 suite reads is one the L1 suite wrote.
# What is only here: a real kubelet restarting a real container after it had been Ready; a real
# deployment controller not having converged yet, which is the only way to assert 04 §5.1's opening
# sentence — the write returned success and the verdict is not Satisfied; a real endpoint-slice
# controller publishing a count from live pod readiness; GKE's full admission chain, against which
# the two-leg admission probe's negative control is a real experiment rather than a simulated one;
# and a real deletion, so a recreated object genuinely gets a new uid.
bash dev/verify/verify-prober-l2.sh gke-scratch-kube-agents-dev

# V-REV-011: a rollback REPLAYS THE PRE-STATE OR REFUSES. The fourth client-side probe, same P1
# waiver, same named successor (broker-execute-l2.sh, P9-T9). Its L1 half is a 28-test hermetic
# suite plus an envtest suite, and that envtest suite is a genuine result — real uids, real
# server-side apply, real field-ownership conflicts. What it cannot reach is the word "pre-state".
# At L1 a successful replay means a field changed; the pre-state of a scaled-down Deployment is
# RUNNING PODS, and only a real controller and a real kubelet put them back, so a replayer that
# wrote the number and restored nothing passes the whole L1 suite. Also only here: a real deletion
# under Foreground propagation with the garbage collector reaping the dependents, which is what
# makes "a name taken since the action" a situation rather than a staging trick; and the read-back
# that L1's fake writer cannot answer — after a redacted Secret snapshot is refused, does the live
# Secret still hold its password, at an unchanged resourceVersion?
bash dev/verify/rollback-replayer-l2.sh gke-scratch-kube-agents-dev

# V-REV-006: a failed rollback PAGES AND AUTO-PAUSES, carried out by a deployed process. The first
# Phase 9 L2 line that is NOT a client-side probe, and therefore the first that needs P1 in full —
# twice over, because C-BR and the operator share one image and a reload that repointed only the
# controller-manager would leave the two halves of this seam on different builds. Its L1 half is
# complete and green (the broker records the escalation against a real CRD; the reconciler fans it
# out) and covers the logic exhaustively; every remaining way for rung 5 to be a no-op lives in the
# five things only a real install has. The load-bearing one is the ServiceAccount NAME: the VAP
# allows the fulfilment write to a CEL string literal, and at L1 the test supplies that same string
# as a fake username, so the policy and the test agree with each other by construction. Here the
# name is whatever kustomize minted, one character of drift makes the ladder silently terminate at
# rung 4, and nothing at L1 can see it. Also only here: 08 §2.7 asked of the live authorizer rather
# than of brake_role.yaml, which is hand-written and so has no `make manifests` run to catch a verb
# it forgot.
bash dev/verify/brake-fanout-l2.sh gke-scratch-kube-agents-dev

# V-BRK-012: one broker per Agent CR, and NO FLEET-WIDE WRITER, in the deployed fleet. The second
# line here that needs P1 in full, and the first that needs it on the BROKER pod rather than only on
# the operator — which is why `_p1_build_inputs` had to learn `kage-broker` before this line could
# exist. The two ends of the image indirection are different subjects: the controller CHOOSES the
# broker image through KUBEAGENTS_BROKER_IMAGE and a pod it renders EXECUTES it, so a controller that
# is the build under test can still be handing out last week's broker digest, and P1 on the operator
# would report green about it.
#
# The L0 half of this row has been green since P9-T7b and is a real result — every broker-derived
# name is a function of the CR, the unpaired render is unrepresentable. It is also exactly what a
# source lint can see, and for four units the deployed fleet had no brokers on any cluster while it
# stayed green: the image variable was set nowhere and the fallback tag is one V-CMP-002 measured as
# unpullable. Nothing but a cluster with two real Agent CRs on it can tell those two states apart.
#
# It runs LAST because it is the only Phase 9 line that seeds and deletes Agent CRs in
# kubeagents-system — the same reason webhook-negatives-l2.sh is last in Phase 8. Its fixture is the
# two SHIPPED manifests co-located in one namespace, which is the only arrangement where a Service
# selector of `role: actor` alone can be caught round-robining one agent's envelopes into another
# agent's broker.

# V-BRK-007/008/009/010/017: what the deployed broker does with a credential. The third line that
