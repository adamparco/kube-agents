# Chat approval for the action broker

The kube-agents action broker parks every `gated` action as `PendingApproval` and waits for a human ([04 §3](spec/04-workflow-model.md)). This document designs the loop that closes that gap — notification out to chat, approve/reject back in — against the Hermes chat stack that ships today, not against the original three-tier fleet design (never merged), whose C15 gateway ([05 §1.8](spec/05-system-architecture.md)) was specified and never built.

Five decisions are fixed. The loop is two components — an approval notifier for delivery and a ChatOps gateway for decision intake — shipped in v1 as one Deployment, one pod, one ServiceAccount. Approval means the phase flip `PendingApproval` → `Pending`, and the broker, never the gateway, resumes the action through its own pipeline. The components hold their own chat credentials in dedicated apps, in standalone deployment and at integration alike; what integration unifies is Secret management (integration.md §6). Delivery targets come from the roster, and a missing or unusable roster is never an open gate. The command surface is typed verbs first; buttons are a later convenience and never the authority.

## 1. What exists and what this doc adds

The contract this design must keep already compiles and is enforced on the branch:

- `ActionRecord.status.approvals` is writable only by `system:serviceaccount:kubeagents-system:kube-agents-chatops-gateway` (`config/policy/vap-agent-scope-journal.yaml:58`). Every other principal is denied, including a human cluster-admin; the normative writer table is [06 §4.3](spec/06-api-and-data-contracts.md).
- The gateway identity may move a record only from `PendingApproval` to `Pending` or `Rejected`, and may only _clear_ `status.contested`, never set it (`vap-agent-scope-journal.yaml:320–342`). It cannot touch `applied` or `verification` — it records a decision about an action; it does not get to describe what the action did.
- Roster semantics live in `k8s-operator/api/broker/v1alpha1/approvalroster_types.go`: `minApprovals` counts distinct principals (`EffectiveMinApprovals()`), `allowSelfApproval` defaults to false (four-eyes, `SelfApprovalAllowed()`), the approval TTL is clamped by `EffectiveTTL()` between the `MinApprovalTTL`/`DefaultApprovalTTL`/`MaxApprovalTTL` constants (per 06 §4.4), and `HasApprover` returns false on a nil roster, fail-closed.

What was missing when this document was first written — no `pipeline.ApprovalNotifier` implementation, no approve/reject chat verb, no gateway workload, no resumption loop — is built as of §6's inventory below; `cmd/broker/wiring.go:343`'s `Approvals: nil` comment is now stale and worth re-reading only as history of why the gateway identity previously existed solely as a principal string in the VAP. What remains genuinely absent is a production-grade Google Chat bearer verifier (§3) and the two chat apps' actual provisioning (§6).

## 2. The approval notifier

The approval notifier is `internal/broker/approval/notify` — a controller in `kubeagents-system` that watches ActionRecords in phase `PendingApproval` and delivers, refreshes, and resolves chat notifications. The in-pipeline seam it implements is small by design:

```go
type ApprovalNotifier interface {
	Notify(ctx context.Context, ar *agentv1alpha1.ActionRecord, roster *agentv1alpha1.ApprovalRoster) error
}
```

(`k8s-operator/internal/broker/pipeline/pipeline.go:168`.) The production implementation of `Notify` is a thin enqueue that never blocks step 7 — at most a nudge to the notifier's work queue. The watch loop is the delivery engine, because `PendingApproval` records also (re)appear after broker restarts and notifier outages, and a pipeline-synchronous notifier misses all of those.

For each parked record the notifier resolves the roster the same way the gateway will: `spec.agentRef` → the broker `Agent` CR → `spec.operations.approvalRosterRef` → the `ApprovalRoster`. Any broken link — missing ref, missing roster, unreadable object — is roster-unusable, sequence 4 below. The delivery target comes from the roster alone: `spec.notify.slack.channel` or `spec.notify.googleChat.space` (`ApprovalNotify`, `SlackNotify`, `GoogleChatNotify` in `approvalroster_types.go`). Absent notify config means no delivery; the action parks and expires.

The message is rendered from the record's structured fields only — `spec.intent`, `spec.classification.class` and its `reasons`, `spec.targets`, `status.approvals.required` (enforcing a floor of `required >= 2` when `spec.attributionUnverified` is true and `!roster.SelfApprovalAllowed()`, even before `status.approvals` is seeded) and `expiresAt`, and the typed approve/reject commands carrying the action ID (`spec.actionId`, the ULID from which `journal.RecordName` derives the `ar-…` name). Chat text is rendered from the record, never the reverse — 06 §4.3's `report` principle — and the message's voice follows [02 §2.5](spec/02-agent-personas.md)'s gated-ask shape: the evidence, the risk class, who was asked, and the typed approve command. When a record reaches a terminal execution or rollback phase (`PhaseVerified`, `PhaseRolledBack`, `PhaseFailed`, or `PhaseUndone`), `RenderMessage` / `Text()` renders the structured 4-beat `ActionReport` (`Noticed`, `Did`, `Verified`, `Undo`) alongside `ActionEscalation` and `status.contested` hints (`/uncontest <record>`), and `notify.Controller` (`relevantPhase`) delivers or updates the notification while skipping routine non-gated actions that never parked in `PendingApproval` (`status.approvals == nil`). On notifier restart, undelivered `PendingApproval` records are re-rendered and re-delivered; when a record leaves `PendingApproval` the notifier edits the message to mark it resolved with the terminal outcome. Deliveries are deduplicated by an idempotence key — the record UID plus a generation of the rendered content (phase and approval counts) — so a flapping watch does not spam the channel.

That dedup key is only as durable as the reconciler's own write to it: `Deliver` runs, then `Store.Save` persists the key, and a crash (or a lost write) between those two calls leaves a message delivered with no record of it. The next reconcile of the same still-`PendingApproval` record sees no prior state and delivers again — a duplicate prompt in the channel, not a duplicate approval, since `ApplyApprove` still de-duplicates by principal regardless of how many times the prompt was posted. Left as a known, self-healing gap rather than a two-phase write: the crash window is narrow, an approver acting on either copy of the prompt is a correct approval, and the stale copy is edited to the terminal outcome the same as the one that got saved.

RBAC: get/list/watch on `actionrecords`, `agents`, and `approvalrosters`. Delivery needs no status write, and delivery state does not go on the record: annotating an ActionRecord would require granting the notifier patch on `actionrecords`, a write grant on the journal that nothing else about delivery needs. Delivery bookkeeping (message timestamps, last-rendered key) lives in a notifier-owned ConfigMap in `kubeagents-system`. The VAP is not widened.

## 3. The ChatOps gateway & zero-inference `a2a/gateway` interception

The ChatOps gateway is `internal/broker/approval/gateway` (the HTTP surface, `cmd/chatops-gateway`) — the one workload that runs as the SA the VAP already names (`isChatOpsGateway`: `system:serviceaccount:kubeagents-system:kube-agents-chatops-gateway`), and the only writer of `status.approvals` and clearer of `status.contested` in the system. It ships in one process with the notifier (`internal/broker/approval/notify` runs as a controller inside the same manager `cmd/chatops-gateway` starts) rather than a second container as first drafted here — one pod, one SA either way, so the boundary is the principal, not the process or container.

Ingress operates in two complementary modes:
1. **Standalone webhook ingress (`cmd/chatops-gateway`):** A dedicated Slack app (`/slack/commands`) and Google Chat app (`/googlechat/events`) whose tokens live in a Secret in `kubeagents-system` held only by the `chatops-gateway` pod.
2. **A2A `mode: next` zero-inference command interception (`a2a/gateway` → `chatops-gateway` + `BROKER` stream):** In `a2a/gateway`, `ParseApprovalCommand(msg.Text)` (`a2a/gateway/text.go`) intercepts `/approve`, `/reject`, `/undo`, `/uncontest`, and `/kage <verb>` (after stripping leading `<@U...>` / `@bot` mentions) inside `Gateway.handleInbound` **strictly before** `lockSession`, `lookupOrMintSession`, and `routeTurn`. Neither well-formed nor malformed approval commands ever touch `KV_session-state` or invoke an LLM worker (zero inference in the approval loop). When intercepted, `a2a/gateway` extracts the verified canonical roster principal `<platform>:<id>` (`CanonicalRosterPrincipal` in `a2a/gateway/principal.go`), mints a root capability entry at `$KV.cap.root.approve-<actionId>-<decisionId>` (`capability.ApprovalRootKey`, `Delegate: "broker"`, `Requester: canonicalPrincipal`), forwards the command via `POST /v1alpha1/commands` to `kube-agents-chatops-gateway` (`Dispatcher.CommandHandler()` in `internal/broker/approval/gateway/dispatch.go`) so `isChatOpsGateway` performs the sanctioned `ActionRecord/status` patch or `UndoRequest` creation, and publishes `ActionApprovalMessage` on `a2a.broker.approve.<namespace>.<actionId>`.

The command grammar is typed-first: `approve <action-id>`, `reject <action-id> [reason]`, `undo <action-id> [reason]`, and `uncontest <action-id>` (all accepting optional leading `/` or `/kage ` prefixes). Block Kit buttons are an optional later convenience and, per 05 §1.8, never the authority — a click delivers an action ID and a claimed principal, and the gateway re-resolves the clicking principal from the platform-verified payload and runs the same authorization pipeline as a typed command.

The principal is extracted from the platform event as the immutable platform ID — Slack user ID → `slack:U…`, Google Chat → `googlechat:users/…`, Discord user ID → `discord:<snowflake>` (`ApproverPlatformDiscord = "discord"` in `approvalroster_types.go`, `DiscordPrincipal` in `principal.go`, and `^(slack|googlechat|discord|k8s):\S+$` in `undorequest_types.go`) — never a display name or email, per 06 §1.2 V-11 and the existing `*_ALLOWED_USERS` convention. Then, per command:

resolve the record → resolve the roster (the §2 chain) → `HasApprover(principal)` → four-eyes: with `allowSelfApproval` false, the requester may not approve — `spec.requester.id` already carries the platform-qualified form (`ActionRequester`, `actionrecord_types.go`), so this is canonical string equality → enforce the `AttributionUnverified` quorum floor (`if ar.Spec.AttributionUnverified && !roster.SelfApprovalAllowed() && required < 2 { required = 2 }` in `ensureApprovals`) → count distinct granted principals against `required` → check the TTL against `status.approvals.expiresAt` (or against `ar.CreationTimestamp.Add(roster.EffectiveTTL())` on the first vote when `status.approvals == nil`, preventing an unseeded record from bypassing TTL before `ResumeController` sweeps it) → write.

The writes match the VAP (`config/policy/vap-agent-scope-journal.yaml`) and L0 parity check (`dev/tests/journal-status-vap-parity.py`) exactly:
- **Approve / Reject (`AuthorizeApprove`, `AuthorizeReject`, `ApplyApprove`, `ApplyReject`):** Appends an `ApprovalEntry{Principal, At, Comment}` to `status.approvals.granted` or `.rejected`. When the distinct granted count reaches `required`, the same update sets phase `Pending`; a reject sets phase `Rejected`.
- **Undo (`AuthorizeUndo`, `Dispatcher.handleUndo`):** Verifies the record is in `PhaseVerified` with a usable `spec.undo` plan (`Strategy != UndoNone`, `len(Steps) > 0`), checks the undo window (`UndoWindowExpiresAt`), and creates an `agentv1alpha1.UndoRequest` CR (`MarkContested: true`) in the record's namespace for `UndoReconciler` (`kube-agents-undo-controller`) to replay. The gateway never sets `status.phase = Undone` directly.
- **Uncontest (`AuthorizeUncontest`, `ApplyUncontest`):** Verifies `status.contested == true` and roster membership, then patches `status.contested = false` via `approval.Write`.

The `chatops-gateway` ClusterRole (`config/chatops-gateway/rbac.yaml`) grants `get`, `list`, `watch` on `actionrecords`, `approvalrosters`, and `agents`; `get`, `list`, `watch`, `create` on `undorequests`; and `patch` on `actionrecords/status` — nothing else, and no patch on `agents`.

Expiry is never an approval, and the gateway never writes `Expired`. Marking overdue `PendingApproval` records `Expired` belongs to the broker's resumption loop (§4, sequence 3) — the owning broker may write phase under the VAP, and `PendingApproval → Expired` is a legal transition per `CanTransitionTo` (`actionrecord_phases.go`).

The resumption loop is the third piece and lives in the broker, not the gateway (`internal/broker/pipeline/resume.go`'s `Pipeline.Resume`, driven by `ResumeController`, both in the broker's own package). The gateway never executes anything; it flips phase. `cmd/broker` polls for the approval signature — phase `Pending` with a populated `status.approvals` block — every 5s (and also receives `a2a.broker.approve.<namespace>.<actionId>` events via `natsadapter.Adapter`), verifying the `$KV.cap.root.approve-<actionId>-<decisionId>` capability (`VerbBrokerApprove = "broker.approve"`, root-only `e.Parent == nil`) when `ApprovalVerifier` is wired. On a signal it re-runs the pipeline from classification, per 06 §4.4: re-classify against live state at approval time, refuse if the class rose, refuse if a target's uid no longer matches (`ActionRecord.spec.targets[].uid`), and update `ar.Spec.PreState` and `ar.Spec.Undo` in-memory during resumption without mutating immutable `.spec` on the API server. Approval is permission, not a bypass. The same loop owns the TTL clock: a `PendingApproval` record past its deadline is moved to `Expired`, computed independently of whether `status.approvals` was ever written, since only the gateway may write it.

## 4. Sequences

1. **Happy path.** Gated envelope → broker parks the record `PendingApproval` (preserving initial `spec.preState` and `spec.undo`), `Notify` enqueues → notifier resolves the roster and posts to `spec.notify`'s channel → an approver types `/approve <action-id>` → `a2a/gateway` intercepts before session/LLM routing, mints `$KV.cap.root.approve-<actionId>-<decisionId>`, forwards `POST /v1alpha1/commands` to `chatops-gateway` (which authorizes roster, four-eyes, `AttributionUnverified` floor, count, and TTL, then patches `status.approvals` and flips phase to `Pending`), and publishes `ActionApprovalMessage` on `a2a.broker.approve.<namespace>.<actionId>` → the broker verifies the approval capability, re-classifies, and executes through steps 8–11 → notifier renders the 4-beat `ActionReport` (`Noticed`, `Did`, `Verified`, `Undo`) and updates the thread.
2. **Reject.** Any roster principal types `/reject <action-id> [reason]` → gateway appends to `rejected` and sets phase `Rejected`, terminal → notifier edits the message and the reason lands in the thread. A re-raise is a new envelope.
3. **Expiry.** TTL passes with insufficient approvals → the broker's resumption loop marks the record `Expired`, terminal (and `AuthorizeApprove`/`AuthorizeReject` refuse any first vote arriving after `CreationTimestamp + EffectiveTTL()` even before the sweep runs) → notifier edits the message. An expired action is re-proposed, not resurrected (04 §3.1): resubmission re-enters the pipeline from the top.
4. **Undo & Uncontest.** A roster principal types `/undo <action-id> <reason>` against a `Verified` record → `chatops-gateway` authorizes via `AuthorizeUndo` and creates an `UndoRequest` CR (`markContested: true`) → `UndoReconciler` replays the validated `UndoPlan`, transitions the `ActionRecord` to `Phase: Undone` with `status.contested: true`, and `cmd/broker`'s `syncContestedIndex` blocks automated re-mutation of the contested target until a roster principal runs `/uncontest <action-id>`, which clears `status.contested = false` via `ApplyUncontest`.
5. **Roster unusable.** Missing `approvalRosterRef`, missing or unreadable roster, or empty approvers → no notification is sent, the record parks and expires. A missing roster is never an open gate — fail-closed row 6, 06 §4.4, and `HasApprover`'s nil-roster-false is the same rule in the gateway.
6. **Notification failure.** Slack down, token revoked, channel deleted → `Notify` returns an error and the action stays parked; the seam's doc comment (`pipeline.go:163–167`) is the normative statement — a broker that could not reach anyone and proceeded anyway has converted "waiting for a human" into "nobody was watching". The watch loop retries delivery with backoff; expiry still governs.

What the submitting agent tells its own requester at each of these outcomes — and how it follows a parked action to its terminal phase — is integration.md §2's caller outcome contract.

## 5. Identity and principal mapping

Roster principals use the canonical platform-prefixed grammar (`slack:U…`, `googlechat:users/…`, `discord:<snowflake>`) and carry different authority from `allowedUsers`: `allowedUsers` gates talking to the agent; the roster gates releasing or undoing a gated action. That is 06 §4.4's two-tier split — braking is wide, proceeding is roster-only — kept intact here.

In `a2a/gateway`, the raw platform sender identity is captured on `InboundMessage.SenderID` before session pseudonymisation (`ev.Message.Sender.Name` in `gchat.go`, `m.User` in `slack.go`, `m.Author.ID` in `discord.go`) and converted via `CanonicalRosterPrincipal` into `<platform>:<id>`. Both `$KV.cap.root.<taskId>` (for task proposals) and `$KV.cap.root.approve-<actionId>-<decisionId>` (for zero-inference approvals) record this canonical `<platform>:<id>` in `Entry.Requester`, never the Session KV HMAC pseudonym.

Self-approval is the same principal string after canonicalization, compared against `spec.requester.id`. A requester with `attributionUnverified: true` still counts for the four-eyes denial: deny on match, never allow on doubt — and when `spec.attributionUnverified` is true and `!roster.SelfApprovalAllowed()`, the gateway enforces a minimum quorum floor of `required >= 2` (`ensureApprovals` in `patch.go` and `RenderMessage` in `render.go`).

## 6. Build inventory

Built: the notifier controller and the shared rendering/roster-resolution/authorization code in `internal/broker/approval` (and its `notify`/`gateway` subpackages, including `POST /v1alpha1/commands` in `gateway/dispatch.go`); zero-inference command parsing (`a2a/gateway/text.go`), canonical principal extraction (`a2a/gateway/principal.go`), and pre-session command interception + `$KV.cap.root.approve-<actionId>-<decisionId>` minting in `a2a/gateway/gateway.go`; the gateway workload in `cmd/chatops-gateway`; the `kube-agents-chatops-gateway` ServiceAccount, ClusterRole (including `undorequests` create), and namespaced Role/bindings in `config/chatops-gateway/`; the L0 VAP/ActionRecordStatus parity harness (`dev/tests/journal-status-vap-parity.py` and `TestActionRecordStatusVAPParity`); the resumption, capability verification, and expiry loop inside the broker (`internal/broker/pipeline/resume.go`, `resume_controller.go`, `internal/broker/natsadapter/adapter.go`, polled from `cmd/broker/resume.go`); and the Deployment/Service manifests in `config/chatops-gateway/deployment.yaml`.

Still absent: the Slack/Google Chat token Secret objects themselves (the Deployment reads them as `optional: true` and the process warns and disables the affected route/platform if they are missing, rather than crash-looping); a production Google Chat JWT verifier (§3's `SharedSecretVerifier` is v1's); and provisioning the two chat apps, which is manual console steps documented alongside the module's deploy manifests, plus a second instance of the `chat-pubsub` Terraform module (`terraform/modules/chat-pubsub`) for the Google Chat topic and subscription.

## 7. Failure modes

Beyond sequence 6:

A compromised gateway is bounded by the VAP and its Role: it can grant or reject approvals — flipping `PendingApproval` to `Pending` or `Rejected` — clear `contested` (`true → false`), and create `UndoRequest` CRs, nothing else; with no patch on `agents`, it cannot unpause an agent. It cannot touch `applied`, `verification`, `timestamps`, or `undoneBy`, cannot directly set `status.phase = Undone`, cannot execute, and cannot approve its way past re-classification, because the broker re-runs the pipeline on resumption. The worst case is a wrongly released action that was already classified, snapshotted, undo-planned, and journaled.

Duplicate approvals do not lower the bar: the threshold is distinct principals, so the same approver typing `approve` twice counts once. Replayed chat events are deduplicated by platform event ID in the gateway before authorization runs. Two gateways would mean two socket connections and split ingress, so the Deployment is single-replica with a leader lease, echoing 05 §1.8's one-socket rule. Clock skew on the TTL is resolved in the broker's favor: the broker's clock governs expiry, the gateway checks both `status.approvals.expiresAt` and `ar.CreationTimestamp.Add(roster.EffectiveTTL())` when `status.approvals == nil`, and a gateway write that lands after the broker marked the record `Expired` fails at admission — the VAP's `oldPhase == 'PendingApproval'` guard makes late approvals fail closed.

A notifier posting to a channel the approvers cannot see is a misconfiguration the system survives (the action expires) but should surface; a roster status condition reporting last delivery outcome is the natural place. Optional, not required for v1.

## 8. Verification

Verification continues under [09 §§3–4 and §9.5](spec/09-verification-and-validation.md)'s discipline — stable IDs, lowest level that proves the property, gate classes, replace-never-delete — but the spec is frozen, so these checks cannot be added to 09's catalog. This doc holds the module's local check index for the approval loop, same ID discipline, `V-CHAT-nnn`. Gated-parks-and-does-not-execute is already V-GAT-003's property and is not renumbered here.

- V-CHAT-001 — a principal not on the roster is refused by the gateway, and the same write attempted directly is denied by the VAP.
- V-CHAT-002 — self-approval is refused when `allowSelfApproval` is false, including for an `attributionUnverified` requester (which also raises the quorum floor to `required >= 2`).
- V-CHAT-003 — expiry is not approval: a record past its TTL becomes `Expired` (and is refused on first vote when `status.approvals == nil` past `CreationTimestamp + EffectiveTTL()`) and never executes, and a late approval write is rejected at admission.
- V-CHAT-004 — the VAP denies `status.approvals` and `status.contested` writes from every non-sanctioned principal, including the owning broker and a human cluster-admin, and `dev/tests/journal-status-vap-parity.py` enforces 1:1 parity between `ActionRecordStatus` JSON fields and `vap-agent-scope-journal.yaml`.
- V-CHAT-005 — notification failure leaves the gate closed: with delivery failing, the record stays `PendingApproval` and expires; nothing executes.
- V-CHAT-006 — an approved action is re-classified before execution; a risen class or a moved `preconditions.uid` refuses the resumption.
- V-CHAT-007 — the roster-unusable path sends nothing and opens nothing: broken ref, empty approvers, and unreadable roster all park and expire.
- V-CHAT-008 — zero-inference interception in `a2a/gateway`: `/approve`, `/reject`, `/undo`, and `/uncontest` (well-formed or malformed) are intercepted before session lookup and LLM routing, mint `$KV.cap.root.approve-<actionId>-<decisionId>`, and forward via `POST /v1alpha1/commands` to `chatops-gateway`.

These land at integration.md §8's phases 2 and 3 — the notifier's checks gate phase 2, the gateway's and the resumption loop's gate phase 3 — before any write authority exists on the path they protect.
