# Action broker: integration seams

## 1. Posture

The kube-agents action broker (`k8s-operator/cmd/broker` and `k8s-operator/internal/broker/`) and the A2A NATS bus/capability plane (`a2a/`) are wired end-to-end across both direct mTLS HTTP (`/v1alpha1/actions`) and the NATS `BROKER` stream (`a2a.broker.>`). This document records the implemented integration seams across the read-only credential proxy, the agent envelope client and skills, the NATS capability assertion verifier and adapter, and the broker pipeline and resumption loop.

The seams follow [07 §5](spec/07-implementation-roadmap.md)'s rule — machinery before authority. No write credential is granted to any agent container; read-only enforcement in the credential proxy, capability verification on NATS, risk classification, write-ahead journaling, dry-run undo validation, and the safety brake execute on every mutation path.

## 2. (a) The caller escalation contract

Callers reach the Action Broker through two authenticated transports that feed the same 11-step `pipeline.Pipeline`:

1. **Direct mTLS HTTP (`/v1alpha1/nonce` + `/v1alpha1/actions`):** An mTLS client certificate plus a projected ServiceAccount token with audience `kubeagents-broker` (`broker.TokenAudience`, `k8s-operator/internal/broker/auth.go`), carrying an action envelope per [06 §4.1](spec/06-api-and-data-contracts.md), POSTed to `/v1alpha1/actions`. `ExpectedCaller` is singular — "the ONE reader identity this broker accepts" (`auth.go:69`). Integration keeps one broker per actor identity ([08 §5.2](spec/08-agent-runtime-and-identity.md)). The caller registry is the broker `Agent` CR: a `PlatformAgent` install registers its agent as a caller by creating a broker `Agent` CR naming the reader SA. The CR is registration and brake surface only — it does not own the agent's Deployment (architecture.md §6).
2. **NATS `BROKER` stream (`a2a.broker.propose.<namespace>.<agent>`):** Session pods and the A2A bridge without direct broker mTLS mounts mint an attenuated capability hop (`VerbBrokerPropose` = `"broker.propose"`, `Delegate: "broker"`, `EnvelopeSHA256: <sha256>`, `Requester: ""`) via `capability.Minter.MintHop` in `a2a propose --file <path|->` (`a2a/cmd/a2a/main.go`) and publish an `ActionProposalMessage` to `a2a.broker.propose.<namespace>.<agent>`.

On the caller pod the mTLS contract is three spec deltas, rendered by the shipping operator: a projected ServiceAccount token volume with audience `kubeagents-broker`; a client-certificate mount — a cert-manager `Certificate` the operator renders, replacing the module's `mesh_trust.go`; and one more egress rule in the operator's `buildNetworkPolicy` allowlist, to the broker Service on 8443.

The interception seam is the credential proxy (the envoy-credential-proxy sidecar plus the wrapper CLIs on the sandbox `PATH`), because it already gates kubectl. Wrapper binaries send command name and argv to Envoy on loopback `127.0.0.1:8765`, which forwards to `agents/platform/scripts/credential_proxy.py`; `agents/platform/scripts/command_policy.py` refuses mutating verbs (rule id `kubernetes.read-only`) whenever `CREDENTIAL_PROXY_ENFORCE_READ_ONLY` is anything but `"false"`. The switch is reserved twice over — named in `SensitiveEnvVars` (`k8s-operator/api/v1alpha1/common_types.go:49`, the webhook rejection) and dropped by `mergeCredentialProxyEnv` (`k8s-operator/internal/controller/platformagent_manifests.go`, the enforcement that holds when the webhook is bypassed) — so the refusal point is stable.

When a mutating `kubectl` subcommand is refused by the read-only gate, `build_broker_escalation_hint(subcommand, args, namespace)` in `agents/platform/scripts/command_policy.py` attaches an `"escalation"` object (including `"endpoint"`, `"skill": "apply-change"`, `"cliHint"`, `"verb"`, `"namespace"`, `"resourceHint"`, and `"requiredFields"`) to the HTTP `403` `read_only_refusal` JSON body in `agents/platform/scripts/credential_proxy.py`. The wrapper client (`agents/platform/scripts/credential_proxy_client.py`) inspects the `403` payload and prints `Hint: <escalation.cliHint>` to `stderr`. **Skill-layer envelope construction is the primary design; proxy-side translation is explicitly rejected as primary.** The agent's skills (`agents/platform/skills/apply-change/SKILL.md` and `a2a/persona/platform/skills/propose-action/SKILL.md`) invoke `agents/platform/scripts/broker_client.py`, a stdlib-only Python client that implements byte-exact RFC 8785 JCS canonicalization (`compute_idempotency_key` matching Go `broker.ComputeIdempotencyKey`), ULID/trace-ID generation, mTLS HTTP submission (`/v1alpha1/nonce` + `/v1alpha1/actions`), and automatic fallback to `a2a propose --file -` over NATS when mTLS credentials are absent.

The escalation skill and `broker_client.py` also own the caller outcome contract: reporting what became of a submission (`--wait` polling `ActionRecord` status or watching `a2a.broker.events.<namespace>.<actionId>`). In `StepClassify` (`k8s-operator/internal/broker/pipeline/pipeline.go`), hard blast-radius cap violations (`classify.AbortError`, reason `blast-radius-cap-exceeded`) return HTTP `422 Unprocessable Entity` (`http.StatusUnprocessableEntity`) rather than `403 Forbidden`, signaling that the action is structurally unprocessable and cannot be escalated to human approval.

## 3. (b) NATS adapter, capability verification, and pipeline resumption

When `NATS_URL` (or `A2A_NATS_URL`) is configured on `kage-broker`, `startNATSAdapter` (`k8s-operator/cmd/broker/wiring.go`, invoked from `main.go`) connects to NATS using the broker's projected token (`NATS_TOKEN_FILE` / `A2A_BUS_TOKEN_FILE` via `nats.TokenHandler` or static credentials) with `nats.CustomInboxPrefix("_INBOX.broker")`, constructs `broker.NewCapabilityAssertionVerifier(nc, "broker")`, and starts `natsadapter.Adapter` (`k8s-operator/internal/broker/natsadapter/adapter.go`):

- **Capability Assertion Verifier (`k8s-operator/internal/broker/assertion.go`):** Queries the out-of-process capability verifier over `a2a.cap.verify.broker` using reply inbox `a2a.cap.reply.broker.<nuid>`. `ParseCapRef` accepts `"cap:<key>#<rev>"`, `"<key>#<rev>"`, `"<key> @<rev>"`, `"<key>@<rev>"`, and JSON object encodings.
  - `VerifyProposal` (`VerbBrokerPropose` = `"broker.propose"`): requires `Allowed: true`, non-empty root-walked `Requester`, and exact `EnvelopeSHA256` match against the raw envelope bytes, returning a canonical `broker.Requester{ID: resp.Requester}` so `StepAuthenticate` sets `AttributionUnverified = false` (whereas unverified HTTP callers remain `AttributionUnverified = true`).
  - `VerifyApproval` (`VerbBrokerApprove` = `"broker.approve"`): verifies the root approval capability (`$KV.cap.root.approve-<actionId>-<decisionId>`) minted by `a2a-gateway` and enforces `Requester == approverPrincipal` (comparing `EnvelopeSHA256` when present on the capability entry).
- **NATS Adapter (`k8s-operator/internal/broker/natsadapter/adapter.go`):** Subscribes to `a2a.broker.propose.<namespace>.<agent>` and `a2a.broker.approve.<namespace>.<actionId>` (queue group `kage-broker`), enforces anti-replay via the shared `broker.ReplayGuard`, journals refusals via `broker.StoreRejectionJournal` and publishes dead-letter diagnostics to `a2a.broker.dlq.<namespace>.<reason>`, and emits lifecycle `ActionEventMessage` payloads to `a2a.broker.events.<namespace>.<actionId>` (also wired as `pipeline.EventPublisher` into `ResumeController` in `k8s-operator/cmd/broker/resume.go`).
- **Immutable `ActionRecord.spec` across `Pipeline.Resume` (`k8s-operator/internal/broker/pipeline/pipeline.go` & `resume.go`):** Because `ActionRecord.spec` is immutable on the Kubernetes API server (`self == oldSelf` CEL rule), `stepGate` preserves the initial `Spec.PreState` and `Spec.Undo` plan when parking a `PendingApproval` record. When `Pipeline.Resume` re-reads live cluster state and re-validates the undo plan after approval, it updates `ar.Spec.PreState` and `ar.Spec.Undo` in-memory for execution and verification while writing only `.status` and `.metadata` to the API server.
- **`ContestedIndex` seeding and synchronization (`k8s-operator/cmd/broker/resume.go`):** `brokerRuntime` exposes `Contested *broker.ContestedIndex` (`wiring.go`), and `syncContestedIndex` runs both at broker startup before serving (`main.go`) and on every `runResumeLoop` tick (`resume.go`). It lists `ActionRecord`s in the broker's namespace, marking targets in `ContestedIndex` when `status.contested == true` and clearing targets when `status.contested == false` (after `/uncontest`), ensuring `ReasonTargetContested` (`403`) survives broker restarts.

## 4. (c) Identity and RBAC

The agent keeps its read-only stack untouched. The KSA `kubeagents-platform-agent` and its read-only ClusterRole are canonical in `docs/site/src/content/docs/reference/security-and-iam.md`; this document does not restate the grants. The actor SA is held only by the broker pod, granted exactly the write set the classifier governs, and mapped to the NATS `broker` identity in `platform-a2a-auth-map` (`k8s-operator/internal/controller/platformagent_a2a_identities.go` & `platformagent_a2a_manifests.go`). The reader never gains a write verb — a write by a reader identity stays an alarm by construction ([03 §3.1](spec/03-security-model.md)).

One current-world wrinkle must be resolved, and it is the single biggest authority migration in the plan. Cluster Agent kubectl authenticates as the **GSA** — `gcloud container clusters get-credentials` puts the Google identity, not the KSA, on the kubeconfig path. On the `gke-admin` permission set the cloud identity therefore already holds writes that the credential proxy merely refuses: the ceiling is policy in a sidecar, not identity. Integration moves that authority. The GSA's permission set drops to read-only, and the broker's own GSA — Workload Identity on the actor SA — takes the write half. This is phase-gated (§9, phase 4 and later) and is never done while the broker is dark: dropping the GSA before the broker can execute leaves the install unable to mutate at all, and granting the broker's GSA before interception is proven duplicates a write path.

## 5. (d) Operator adoption

A `PlatformAgent` install grows a broker when the shipping operator renders one more workload per install: the broker Deployment and Service, reusing `broker_manifests.go`'s shapes — `buildBrokerService` (the `<agent>-broker` ClusterIP on :8443), `buildBrokerDeployment` with TLS Secrets mounted by name, and the `buildWaitForBrokerContainer` pattern for startup gating — plus the broker `Agent` CR that registers the caller (§2).

The rest of `internal/broker/controller`'s rendering is the workload-pair machinery the module carries from the original three-tier fleet design (never merged), and it is dropped or replaced in the same series: `agent_manifests.go` (agent-pod rendering — the shipping operator owns pod rendering for `PlatformAgent`), `pod_launcher.go`'s agent half, and `mesh_trust.go` / `pair_netpol.go`, replaced by chart- or operator-rendered equivalents scoped to the broker pair. Cert issuance and the broker-ingress NetworkPolicy survive as requirements ([08 §2.3](spec/08-agent-runtime-and-identity.md)); what changes is their renderer. What survives as-is: `broker_manifests.go`, every reconciler except `AgentReconciler`'s workload-pair half, and the two ValidatingAdmissionPolicies.

Manifest ownership follows the repository's one-engine rule: the Helm chart (`charts/kube-agents`) grows the broker templates, and `config/` remains the kustomize dev path, kept in step by `./hack/sync-chart-manifests.sh`.

## 6. (e) CRD cohabitation

Both API packages register kinds into the one group `kubeagents.x-k8s.io`, and there are no kind collisions today: the shipping operator's `PlatformAgent` and `AgentPlugin` against the broker module's `Agent`, `ActionRecord`, `ApprovalRoster`, `ChangePolicy`, `FleetFreeze`, and `UndoRequest`. Beyond the group, the one shared surface is the manager ClusterRole/webhook config. The standing hazard is structural: two Go packages (`api/v1alpha1` and `api/broker/v1alpha1`) registering into one group-version. Scheme registration must remain additive — neither package may claim a kind the other registers — and the CRD YAMLs live side by side in `config/crd/bases/`.

Three shapes exist for the Go packages later, stated as options with a recommendation. (i) Keep two packages indefinitely — recommended until the fleet-era fields the broker `Agent` still carries (`parentRef`, `harness`, `deployment`, `integration`; architecture.md §6) are pruned, because merging first imports fields the module's boundary excludes. (ii) Merge into one `api/v1alpha1` once `AgentSpec` stabilizes at its caller-registration shape. (iii) Rename the group — never; the group is the compatibility surface every installed CRD and every VAP binding names. The broker `Agent` kind is likewise not renamed against `PlatformAgent`; prose disambiguates ("the broker `Agent` CR"), and the kinds serve different owners.

## 7. (f) Chat wiring

The approval loop's contract — components, verbs, sequences, failure modes — is chat-approval.md's. Inbound approval commands (`/approve`, `/reject`, `/undo`, `/uncontest`, and `/kage <verb>`) are intercepted deterministically at the top of `a2a/gateway` (`Gateway.handleInbound`) with zero LLM inference, minting `$KV.cap.root.approve-<actionId>-<decisionId>`, forwarding to `kube-agents-chatops-gateway` (`POST /v1alpha1/commands`, running as `system:serviceaccount:kubeagents-system:kube-agents-chatops-gateway` to satisfy `isChatOpsGateway` in `vap-agent-scope-journal.yaml`), and publishing `ActionApprovalMessage` to `a2a.broker.approve.<namespace>.<actionId>`.

Chat-approval.md §5 names the identity constraint: the relay path pseudonymises chat identities (the Session KV HMAC salt), while roster authorization requires canonical `<platform>:<id>` identities (`slack:U...`, `googlechat:users/...`, `discord:...`); `a2a/gateway` extracts the canonical principal before session hashing and stamps it onto both root capability entries and ChatOps command requests. For outbound delivery, the notifier (`k8s-operator/internal/broker/approval/notify/controller.go`) posts both initial gate prompts and terminal 4-beat `ActionReport` notifications (`PhaseVerified`, `PhaseRolledBack`, `PhaseFailed`, `PhaseUndone`) directly without depending on an LLM turn.

## 8. (g) Journal and audit export

`ActionRecord.status.exported` is the durability receipt, and nothing writes it against a real sink today: `internal/journal/export.go` defines `AuditSink` and `ExportEntry` with only `WriterSink` and `MemorySink` behind them (not built: a production sink). Integration names one, and the decision is **Cloud Logging first** — the install already ships a fluent-bit sidecar, and the SLI model in [05 §5.1](spec/05-system-architecture.md) reads audit logs, so the first sink lands where the alerts already look. A dedicated GCS or BigQuery sink is the later option, not the first. `internal/journal/cloudaudit` and `completeness.go` (`CheckCompleteness`) are the building blocks of the C-JR completeness join (spec vocabulary, 05 §1.6): once export flows, the same series can wire the reconciliation of audit logs against exported records — the detective half of the enforcement boundary 03 §4.3 states honestly, since deletes, subresources, and cloud writes are detect-only at admission.

Retention stays gated on `exported.confirmed`. No sink means nothing is ever deleted — correct degradation, and the operating rule for phase-1 installs without a sink: records accumulate, and the retention controller starts deleting only after an export sink is wired and confirming.

## 9. (h) Phased adoption plan

Five phases, each independently landable. Checks named here get stable IDs in the module's local check index (the rule chat-approval.md §8 sets, since [09 §4](spec/09-verification-and-validation.md)'s catalog is frozen), run at the lowest level that proves the property, and carry 09 §9.5's gate classes. Every phase gate is BLOCKING-PHASE: the next phase does not start until the gate is green, and no phase advances on red (07 §5).

1. **Standalone shadow.** The module is installed alongside a real install; broker `Agent` CRs carry `dryRunOnly: true` — shadow mode, every submission forced to an effective dry run per `shadowed()` (`k8s-operator/internal/broker/pipeline/pipeline.go:344`); the actor SA is bound to empty roles; envelopes come only from test callers. Landing surface: the chart. Gate: the pipeline e2e suite green with zero write verbs anywhere — 07 §5's P8-T6-style pre-merge check, tightened from "no write verb before machinery" to no write verb, full stop.

2. **Notifier.** The approval notifier (chat-approval.md §2) ships; gated dry-run actions produce chat prompts and terminal 4-beat `ActionReport` summaries. Landing surface: the chart plus a `kubeagents-system` Deployment. Gate: the notification-failure-closed and roster-unusable sequences (chat-approval.md §4, sequences 4 and 5) proven against a live channel.

3. **Gateway verbs.** Approve, reject, undo, and uncontest go live via zero-inference `a2a/gateway` interception and `kube-agents-chatops-gateway` (`POST /v1alpha1/commands`); the VAP is enforced in a real cluster; the broker's NATS adapter and resumption loop execute approved actions and `syncContestedIndex` reconciles contested targets across restarts. Landing surface: the chart plus the gateway workload. Gate: the VAP negative suite — every non-gateway principal denied, including a human cluster-admin — plus four-eyes, unverified-attribution quorum floor (`required >= 2`), and expiry-is-not-approval.

4. **Credential-proxy interception.** Mutating kubectl is refused with the §2 `escalation.cliHint` payload; `broker_client.py` and the `apply-change` / `propose-action` skills submit canonical RFC 8785 JCS envelopes over mTLS HTTP or NATS `a2a propose --file -`; the actor SA gains its first narrow write set, smallest blast radius first (echoing 07's phase 10). Landing surface: `agents/` skills, the proxy policy, and the operator — the §2 pod-spec deltas: the projected token volume, the client-certificate mount, and the broker egress rule. Gate: a reader-identity write attempt fails structurally, every mutation on the granted set is journaled, and an undo round-trips on that set.

5. **Operator-managed.** The shipping operator renders the broker Deployment, Service, and broker `Agent` CR per install (§5); the transitional rendering code — `agent_manifests.go`, `pod_launcher.go`, `mesh_trust.go`, `pair_netpol.go` — is deleted in the same series; the GSA authority migration (§4) happens here, not earlier. Landing surface: the operator plus the chart. Gate: one broker per actor identity asserted fleet-wide (08 §5.2), and live validation on a real install per repository policy.
