# Action broker: integration seams

## 1. Posture

The kube-agents action broker is isolated on the `broker` branch: nothing in the shipping operator (the `PlatformAgent` reconciler in `k8s-operator/internal/controller/`) or the agent path calls it. This document names the seams through which a later PR series wires it in, concretely enough that the series does not re-derive the design. Every anchor below is a current-world file; none of the wiring exists.

The seams are ordered by [07 §5](spec/07-implementation-roadmap.md)'s rule — machinery before authority. No write credential is granted to any path before the classifier, journal, undo path, and brake exist and are tested. On this branch they exist and are tested, so the ordering does a slightly different job than it did in the spec: chat approval (§6) and kubectl interception (§2) land while the broker still holds narrow or no authority, and the authority migrations (§3) come last.

## 2. (a) The caller escalation contract

The contract a caller must satisfy is fixed by what compiles today: an mTLS client certificate plus a projected ServiceAccount token with audience `kubeagents-broker` (`broker.TokenAudience`, `k8s-operator/internal/broker/auth.go`), carrying an action envelope per [06 §4.1](spec/06-api-and-data-contracts.md), POSTed to `/v1alpha1/actions`. `ExpectedCaller` is singular — "the ONE reader identity this broker accepts" (`auth.go:69`). Integration keeps one broker per actor identity ([08 §5.2](spec/08-agent-runtime-and-identity.md)); what changes is where the caller is declared. The caller registry is the broker `Agent` CR: a `PlatformAgent` install registers its agent as a caller by creating a broker `Agent` CR naming the reader SA (at integration). The CR is registration and brake surface only — it does not own the agent's Deployment (architecture.md §6).

On the caller pod the contract is three spec deltas, rendered by the shipping operator at integration: a projected ServiceAccount token volume with audience `kubeagents-broker`; a client-certificate mount — a cert-manager `Certificate` the operator renders, replacing the module's `mesh_trust.go`; and one more egress rule in the operator's `buildNetworkPolicy` allowlist, to the broker Service on 8443.

The interception seam is the credential proxy (the envoy-credential-proxy sidecar plus the wrapper CLIs on the sandbox `PATH`), because it already gates kubectl. Wrapper binaries send command name and argv to Envoy on loopback `127.0.0.1:8765`, which forwards to `agents/platform/scripts/credential_proxy.py`; `agents/platform/scripts/command_policy.py` refuses mutating verbs (rule id `kubernetes.read-only`) whenever `CREDENTIAL_PROXY_ENFORCE_READ_ONLY` is anything but `"false"` (`credential_proxy.py:1373`). The switch is reserved twice over — named in `SensitiveEnvVars` (`k8s-operator/api/v1alpha1/common_types.go:49`, the webhook rejection) and dropped by `mergeCredentialProxyEnv` (`k8s-operator/internal/controller/platformagent_manifests.go:2372`, the enforcement that holds when the webhook is bypassed) — so the refusal point is stable enough to build on. The proxy's wrapper mechanics and kubeconfig sanitization are canonical in `docs/credential-isolation-design.md`; this document names only the refusal point being repurposed.

At integration, a refused mutating kubectl returns an **escalation hint** naming the broker path — which envelope fields to fill, where to submit — instead of a bare `SECURITY_POLICY_BLOCKED`. Two candidates exist for who builds the envelope, and the decision is made here: **skill-layer envelope construction is the primary design; proxy-side translation is explicitly rejected as primary.** A new skill in the agent's skill layer constructs envelopes deliberately, because `intent`, `rationale`, `trigger`, and `requester` are the agent's to state. A mechanical kubectl→envelope translation in the proxy launders intent: `intent` becomes the command string. Classification never reads `intent` — 06 §4.2's inputs are targets and live state — so the laundering is not a security hole; it is a reporting failure, because the approval prompt, the journal, and the four-beat report all render from `spec.intent`. And the proxy cannot supply `trigger` or `requester` honestly: it sees argv, not whether a human asked. If a proxy-side translator is ever built as the fallback, its prerequisite is already flagged in the tree — the comment above `credentialProxyPolicyJSON` (`platformagent_manifests.go:145`) calls for replacing shell-string regex matching with tool-specific argument parsing.

The escalation skill also owns the caller outcome contract: reporting what became of a submission. The caller's reader identity gets get and watch on its own ActionRecords — scoped by the tier and scope labels `journal.Store` derives from `spec.agentIdentity` — so the skill can follow a parked action to its terminal phase. Per the `ActionResponse` decision (06 §4.1): a refusal surfaces the refusal reason verbatim; an executed action is confirmed with its verification outcome; a `pending-approval` decision reports "parked as `ar-<id>`, roster `<name>` notified, expires at `<t>`" and follows the record by watch. The roster's notify channel is not necessarily the requester's channel — the requester learns the outcome from the agent that submitted, not from the approval thread.

## 3. (b) Identity and RBAC

The agent keeps its read-only stack untouched. The KSA `kubeagents-platform-agent` and its read-only ClusterRole are canonical in `docs/site/src/content/docs/reference/security-and-iam.md`; this document does not restate the grants. The actor SA is new (at integration), held only by the broker pod, granted exactly the write set the classifier governs. The reader never gains a verb — a write by a reader identity stays an alarm by construction ([03 §3.1](spec/03-security-model.md)).

One current-world wrinkle must be resolved, and it is the single biggest authority migration in the plan. Cluster Agent kubectl authenticates as the **GSA** — `gcloud container clusters get-credentials` puts the Google identity, not the KSA, on the kubeconfig path. On the `gke-admin` permission set the cloud identity therefore already holds writes that the credential proxy merely refuses: the ceiling is policy in a sidecar, not identity. Integration moves that authority. The GSA's permission set drops to read-only, and the broker's own GSA — Workload Identity on the actor SA — takes the write half. This is phase-gated (§8, phase 4 and later) and is never done while the broker is dark: dropping the GSA before the broker can execute leaves the install unable to mutate at all, and granting the broker's GSA before interception is proven duplicates a write path.

## 4. (c) Operator adoption

A `PlatformAgent` install grows a broker when the shipping operator renders one more workload per install (at integration): the broker Deployment and Service, reusing `broker_manifests.go`'s shapes — `buildBrokerService` (the `<agent>-broker` ClusterIP on :8443), `buildBrokerDeployment` with TLS Secrets mounted by name, and the `buildWaitForBrokerContainer` pattern for startup gating — plus the broker `Agent` CR that registers the caller (§2).

The rest of `internal/broker/controller`'s rendering is the workload-pair machinery the module carries from the original three-tier fleet design (never merged), and it is dropped or replaced in the same series: `agent_manifests.go` (agent-pod rendering — the shipping operator owns pod rendering for `PlatformAgent`), `pod_launcher.go`'s agent half, and `mesh_trust.go` / `pair_netpol.go`, replaced by chart- or operator-rendered equivalents scoped to the broker pair. Cert issuance and the broker-ingress NetworkPolicy survive as requirements ([08 §2.3](spec/08-agent-runtime-and-identity.md)); what changes is their renderer. What survives as-is: `broker_manifests.go`, every reconciler except `AgentReconciler`'s workload-pair half, and the two ValidatingAdmissionPolicies.

Manifest ownership follows the repository's one-engine rule: the Helm chart (`charts/kube-agents`) grows the broker templates, and `config/` remains the kustomize dev path, kept in step by the existing chart-check convention.

## 5. (d) CRD cohabitation

Both API packages register kinds into the one group `kubeagents.x-k8s.io`, and there are no kind collisions today: the shipping operator's `PlatformAgent` and `AgentPlugin` against the broker module's `Agent`, `ActionRecord`, `ApprovalRoster`, `ChangePolicy`, `FleetFreeze`, and `UndoRequest`. Beyond the group, the one shared surface is the manager ClusterRole/webhook config. The standing hazard is structural: two Go packages (`api/v1alpha1` and `api/broker/v1alpha1`) registering into one group-version. Scheme registration must remain additive — neither package may claim a kind the other registers — and the CRD YAMLs live side by side in `config/crd/bases/`.

Three shapes exist for the Go packages later, stated as options with a recommendation. (i) Keep two packages indefinitely — recommended until the fleet-era fields the broker `Agent` still carries (`parentRef`, `harness`, `deployment`, `integration`; architecture.md §6) are pruned, because merging first imports fields the module's boundary excludes. (ii) Merge into one `api/v1alpha1` once `AgentSpec` stabilizes at its caller-registration shape. (iii) Rename the group — never; the group is the compatibility surface every installed CRD and every VAP binding names. The broker `Agent` kind is likewise not renamed against `PlatformAgent`; prose disambiguates ("the broker `Agent` CR"), and the kinds serve different owners.

## 6. (e) Chat wiring

The approval loop's contract — components, verbs, sequences, failure modes — is chat-approval.md's, and its chat apps stay dedicated at integration: a Slack app in socket mode and a Google Chat app with its own Pub/Sub topic and subscription, both the gateway's alone (chat-approval.md §3). Sharing the install's apps does not work: Slack treats a second socket-mode connection on one app as an HA replica — each event goes to exactly one socket, so the gateway and the existing ingress would steal each other's messages — and a second subscription on the existing topic would deliver all chat traffic, raw platform IDs included, to the gateway. Credential unification is limited to Secret management: the gateway's tokens are provisioned and rotated the way the install's other chat Secrets are, not merged into them. Provisioning is manual console steps documented alongside the module's deploy manifests, plus a second instance of the `chat-pubsub` Terraform module (`terraform/modules/chat-pubsub`) for the Google Chat half.

Chat-approval.md §5 names the other constraint: the relay path pseudonymises chat identities (the Session KV HMAC salt), and the gateway needs raw platform IDs to check a roster; a relay-side raw-principal surface is rejected because it widens a privacy seam that exists on purpose. For outbound delivery, the cron relay (`deploy/docker/plugins/chat/`, posting to the Session KV `/v1/cron-reports` route at `agents/platform/scripts/session_kv_server.py:1421`) is precedent only. The notifier posts directly; it must not depend on a Hermes turn to deliver a gate prompt, because the brake and its gates never depend on the agent being healthy.

## 7. (f) Journal and audit export

`ActionRecord.status.exported` is the durability receipt, and nothing writes it against a real sink today: `internal/journal/export.go` defines `AuditSink` and `ExportEntry` with only `WriterSink` and `MemorySink` behind them (not built: a production sink). Integration names one, and the decision is **Cloud Logging first** — the install already ships a fluent-bit sidecar, and the SLI model in [05 §5.1](spec/05-system-architecture.md) reads audit logs, so the first sink lands where the alerts already look. A dedicated GCS or BigQuery sink is the later option, not the first. `internal/journal/cloudaudit` and `completeness.go` (`CheckCompleteness`) are the building blocks of the C-JR completeness join (spec vocabulary, 05 §1.6): once export flows, the same series can wire the reconciliation of audit logs against exported records — the detective half of the enforcement boundary 03 §4.3 states honestly, since deletes, subresources, and cloud writes are detect-only at admission.

Retention stays gated on `exported.confirmed`. No sink means nothing is ever deleted — correct degradation, and the operating rule for phase-1 installs without a sink: records accumulate, and the retention controller starts deleting only after an export sink is wired and confirming.

## 8. (g) Phased adoption plan

Five phases, each independently landable. Checks named here get stable IDs in the module's local check index (the rule chat-approval.md §8 sets, since [09 §4](spec/09-verification-and-validation.md)'s catalog is frozen), run at the lowest level that proves the property, and carry 09 §9.5's gate classes. Every phase gate is BLOCKING-PHASE: the next phase does not start until the gate is green, and no phase advances on red (07 §5).

1. **Standalone shadow.** The module is installed alongside a real install; broker `Agent` CRs carry `dryRunOnly: true` — shadow mode, every submission forced to an effective dry run per `shadowed()` (`k8s-operator/internal/broker/pipeline/pipeline.go:344`); the actor SA is bound to empty roles; envelopes come only from test callers. Landing surface: the chart. Gate: the pipeline e2e suite green with zero write verbs anywhere — 07 §5's P8-T6-style pre-merge check, tightened from "no write verb before machinery" to no write verb, full stop.

2. **Notifier.** The approval notifier (chat-approval.md §2) ships; gated dry-run actions produce chat prompts; nobody can approve yet, so every prompt expires. Landing surface: the chart plus a `kubeagents-system` Deployment. Gate: the notification-failure-closed and roster-unusable sequences (chat-approval.md §4, sequences 4 and 5) proven against a live channel.

3. **Gateway verbs.** Approve and reject go live — the v1 surface; resume and uncontest are v2 of the chat surface (chat-approval.md §3); the VAP is enforced in a real cluster; the broker's resumption loop executes approved actions that are still dry-run. Landing surface: the chart plus the gateway workload. Gate: the VAP negative suite — every non-gateway principal denied, including a human cluster-admin — plus four-eyes and expiry-is-not-approval.

4. **Credential-proxy interception.** Mutating kubectl is refused with the §2 escalation hint; the skill-layer envelope client lands under `agents/`; the actor SA gains its first narrow write set, smallest blast radius first (echoing 07's phase 10). Landing surface: `agents/` skills, the proxy policy, and the operator — the §2 pod-spec deltas: the projected token volume, the client-certificate mount, and the broker egress rule. Gate: a reader-identity write attempt fails structurally, every mutation on the granted set is journaled, and an undo round-trips on that set.

5. **Operator-managed.** The shipping operator renders the broker Deployment, Service, and broker `Agent` CR per install (§4); the transitional rendering code — `agent_manifests.go`, `pod_launcher.go`, `mesh_trust.go`, `pair_netpol.go` — is deleted in the same series; the GSA authority migration (§3) happens here, not earlier. Landing surface: the operator plus the chart. Gate: one broker per actor identity asserted fleet-wide (08 §5.2), and live validation on a real install per repository policy.
